This directory holds data/column.csv and the queries q1.txt, with the expected output in gold1.txt. These files are generated for you by setup.py: do not change setup.py or these files. The CMake project here already builds `setup`; keep it and add the executable target `fl_query` (C++17, standard library only, built with -O2 or better, source files listed in CMakeLists.txt).
`fl_query <csv-file> <queries-file>...` loads the CSV (header `v`, one integer per line: a single column, sorted ascending), runs every query of every queries file in order and prints one line per query, `Q<n>: <result>`, with n counting from 1 across all files.
Query language: one query per line, ending in `;`. Exactly three forms: `SUM(v);` and `SUM(v) WHERE v <op> <integer>;`, with op one of = < <= > >= , or `SUM(v) WHERE v BETWEEN <a> AND <b>;` (inclusive, and that AND is part of the predicate). Parse SUM(v), then WHERE, then the required v identifier before checking for a comparison operator or BETWEEN. In particular, `SUM(v) WHERE v BETWEEN 501 AND 96488;` must parse successfully with inclusive bounds 501 and 96488. Do not check for BETWEEN immediately after WHERE or treat BETWEEN as a comparison operator. Validate this regression and every query kind against gold1.txt before finishing. Sums are exact 64-bit integers (int64_t, never double/float), printed as plain decimal integers (no scientific notation), 0 for an empty selection. A queries file holds MANY queries, one per line: read it line by line and run every line, never the whole file as one query. The sum is over the whole column, or over the contiguous row range the predicate selects (the column is sorted, so a predicate always selects one range, possibly empty: e.g. BETWEEN 5 AND 4, a value that does not exist, or everything). Sum only the blocks that overlap that range, using the block minimums (stored in the block headers) to find them, and handle the first and last block partially; sum each block while decoding it, without materializing the column. A binary search over block minimums plus a search inside the block is fine; a learned index comes in the next stage.
Storage (the FastLanes layout from Afroozeh & Boncz, VLDB 2023): the column is stored as blocks of 1024 values (the last block is padded), each block frame-of-reference encoded (subtract the block minimum, keep it in a per-block header with the bit width W, the smallest that fits) and bit-packed in the Unified Transposed Layout with 64-bit lanes. Unified Transposed order: with ORD = {0,4,2,6,1,5,3,7}, the value at (row r in 0..63, lane l in 0..15) is original position idx(r,l) = ORD[r/8]*16 + (r%8)*128 + l, which covers 0..1023 exactly once. Each of the 16 lanes holds its 64 values (rows 0..63) packed at W bits into W uint64 words; the words of the 16 lanes are interleaved, so word w of lane l is at buffer[w*16 + l]. Decoding is then 16 independent lanes of 64 values in fixed-width, branch-free loops the compiler can auto-vectorize, and a decoded block is scattered back through idx or consumed in transposed order, since sum and count do not depend on order. Queries must scan these encoded blocks, decoding block by block, not a plain int64 array kept beside them.
Structure the program so it can be measured and optimized later: separate functions for the phases load (read the file), parse (text to integers), encode (build the blocks), index build, and query (parse a query, find its row range, sum it), with the encoded blocks in contiguous storage and no global state between them.
Done means `fl_query data/column.csv q1.txt > output1.txt` writes output1.txt, identical to gold1.txt. Implement the language in general; do not special-case these queries or the data.
